# GitHub createCommitOnBranch: separate future action, not exact-commit push

Research only; public GitHub documentation fetched without credentials. No authenticated read, mutation, Git push, target lookup, or live repository effect was performed. A private test repository and its default `main` branch were created and verified during the earlier operator setup. This documentation-only research did not independently recheck their current identity, branch state, permissions or policy. This is not authorization to access them. No implementation is proposed as ready to ship.

## Verdict

**Potentially useful but not established as sound under a strict identity-and-history-bound action contract.** GitHub documents a single mutation which creates a *new* commit whose parent is the branch HEAD and advances that branch, addressed by a Ref global node ID, with a required `expectedHeadOid` [1,2]. It is not a push of a selected existing Git commit: GitHub constructs the commit and controls author/committer; its OID is not an input. An existing exact-SHA push grant cannot authorize it. The documentation inspected does not establish the Ref ID's deletion/recreation/rename/transfer lifetime, an ABA-resistant version, or a guarantee binding a node ID to a previously approved repository incarnation throughout the write. Thus, if the owner requires an immutable incarnation and no intervening movement, **stop: no documented mechanism here meets that contract**. Reading immediately before and after does not close the race. A deliberately weaker contract needs a separate owner security decision, not a silent substitution.

## What is documented, and what is not

* **Target and head:** `branch` is a `CommittableBranch`, supplied either as Ref `id` or repository name with owner plus branch name; it must be under `refs/heads/`. The mutation appends to that branch and updates it; `expectedHeadOid` is the commit OID expected at its head prior to commit [1,2]. Use only the node-ID form, never a name fallback. The documentation describes an expected-head precondition, not an immutable ref generation or sequence counter; no explicit ABA protection was found. A -> B -> A can leave the same OID and cannot be distinguished by head equality alone. Nor does a separately observed matching head prove continuous equality. Do not claim stronger atomic compare-and-swap details or deletion/recreation behavior than the cited text states.
* **Ref identity:** `Ref` exposes `id`, `name`, `prefix`, `repository` and `target`; global node IDs can be used for direct node lookup [2,3]. These permit checking a freshly returned node type, exact fully qualified branch name, repository identity and current head. They do not document that a Ref ID is never reused or remains stable through delete/recreate, rename, transfer or migration, or that lookup and mutation checks are one transaction. GitHub's node ID migration guide explicitly discusses ID formats changing [4]; treat IDs as opaque, not decoded names or a lifetime certificate. Repository IDs and routing names have their own lifecycle uncertainties. A matching ID on a preflight is useful evidence, not a documented incarnation guarantee.
* **File changes:** `FileAddition` contains only path and complete padded RFC 4648 base64 bytes; an existing file at the path is replaced. `FileDeletion` contains only path; a missing deletion path aborts the commit. Paths are root-relative with `/`, unique across both lists. Deletion plus addition at different paths models rename; no character conversion or line-ending normalization is performed, and binary is allowed [2]. Empty fileChanges can make an empty commit, so reject it if not expressly approved.
* **Modes and links:** These inputs expose no mode, object type, executable-bit, symlink or gitlink selector [2]. The cited mutation documentation does not specify output mode for additions or replacements, mode preservation, handling of a symlink at the path or in an ancestor, or link/gitlink deletion. Do not assume mode 100644, preservation of 100755, symlink following or no-follow behavior, nor that deletion of a symlink is supported. A narrow design may refuse paths with non-regular tree entries or non-tree ancestors, and require a reviewed provider contract establishing exact modes for even permitted additions/replacements; local `lstat` alone does not establish remote tree semantics. Until mode semantics are documented to meet the approved result, refuse those operations, rather than discovering a mismatch only after publication. Verification after the write is evidence, not preventive control.
* **Limits:** Inputs specify full base64 content; budget encoding expansion, JSON/request overhead and memory, using strict local per-file, total-byte, file-count and message caps. The cited schema does not state a definitive mutation-specific file count or payload limit; do not invent one or treat general GraphQL node/connection limits as file-addition limits. GitHub documents point/rate limits, resource limits and a nominal 10-second timeout which may change [5]. A 200 can carry GraphQL errors; rate and timeout responses do not establish no side effect [5,6]. Do not split a rejected or too-large proposal into multiple commits without new explicit approval: that changes the operation and atomicity.
* **Author and signing:** GitHub says the credential owner authors the new commit and the committer matches web-interface commits; neither is configurable and no future support is planned. GitHub automatically signs *if supported*, and then marks it verified [1]. Neither a particular user, email, exact commit metadata/OID, unconditional verified signature, nor a deploy-key equivalence is established. Display credential principal, expected attribution and signing uncertainty for approval; use only an API credential whose target access is separately configured and verified, and never log it. Respect branch rules and rejection; do not bypass them.
* **Lost response and idempotency:** `clientMutationId` is described as a unique identifier for the client; the mutation also returns a `clientMutationId` field [1], not as a server-side deduplication key or queryable receipt. Do not claim exactly-once delivery, retry safety, or infer success solely because a current head or matching contents exist. A timeout, dropped response, server error, partial GraphQL response or crash after dispatch is **unknown**, even if a subsequent head equals the old value: another actor could have moved it back. The expected OID may reject a repeat if the first succeeded and the branch still points elsewhere, but ABA defeats that argument. Never automatically resend an ambiguous mutation, including with the same `clientMutationId`.

## Proposed future action contract (conditional on an explicitly accepted weaker identity model)

1. **Selection and preview:** Owner independently configures a dedicated GitHub API credential with least necessary repository permissions; the selected private target must be freshly verified under a separately authorized authenticated read. Record endpoint, opaque repository node ID and canonical owner/name, opaque branch Ref ID, full `refs/heads/main`, current commit OID and credential principal/version. Resolve node by ID and validate type, repository ID/name, prefix/name and commit target; refuse absent, null, mismatch, ambiguity or changed binding. The action is disabled by default; all Pilot owner-only auth, CSRF, scope and secret-handling rules remain. Node ID addresses the mutation itself, but is not evidence of a perpetual identity guarantee.
2. **Freeze the precise new-commit intent:** Preview and approve a new, distinct action kind scoped to project/session/operation and single use, with a short expiry. Bind endpoint, repository ID *and* observed name, Ref ID *and* full ref name, exact expected head OID, credential version/principal, exact message headline/body bytes, ordered normalized additions/deletions, raw content digests and lengths, full bytes in protected bounded durable storage, and a canonical intent digest. Display paths, bytes/diffs, deletions and attribution/signing limits. Refuse unsafe paths, duplicates, symlinks, non-regular entries, submodules, unsupported mode changes, unknown mode semantics, oversized content, empty intent unless explicitly authorized, or state that cannot be evaluated. A digest without durable immutable bytes is not replayable proof. This proposal binds the desired file effect and parent, **not a preexisting commit OID**. No unrelated files or history are authorized; never expose private file contents or tokens in logs.
3. **Preflight and one dispatch:** After consumption and durable admission, perform fresh authenticated node-by-ID checks against every bound value and expected head; revalidate frozen payload and credential. Any mismatch or uncertainty refuses without sending. Use `createCommitOnBranch` with `{branch:{id}, expectedHeadOid, message, fileChanges, clientMutationId}` once. Never substitute owner/name, ref name, another credential, modified payload, or an automatic fallback. This preflight narrows races but cannot prove no delete/recreate, ABA or reassignment between observation and write. In a contract that cannot accept that limitation, do not dispatch at all.
4. **Evidence and recovery:** Atomically record single-use approval consumption, immutable intent and attempt admission before external dispatch, and durable dispatch-start before the network call. A crash after dispatch-start, including before the request actually leaves, is conservatively unknown. Disable automatic retries at HTTP client, SDK, proxy and application layers. Store bounded sanitized response evidence, returned commit OID, branch/ref identity and request correlation only when available. Confirm success only from a complete, attributable mutation success payload and durable receipt; independently read and compare parent, tree, bytes and modes for evidence, not as proof that no race occurred. Treat malformed, partial, transport failure, crash or unclassified GraphQL errors as unknown. A documented pre-execution validation rejection may be recorded as rejected only when the response proves the mutation was not run; otherwise unknown. No compensation, replay or fresh action under the old grant.
5. **Operator attention:** On unknown, preserve evidence and block automatic retry. A later separately authorized read of node/head/history may help the owner investigate, but matching commit message/tree/parent, `clientMutationId`, or current head is not conclusive causation or absence. No automatic reconciliation to succeeded/failed based on those observations. Any new attempt requires a new review and approval of fresh identity, head and complete payload; do not promise exactly once.

## Feasibility gates and test plan (not executed)

Before implementation, obtain an owner decision on whether absence of an ABA/incarnation guarantee is acceptable; independently establish documented identity/write semantics, regular-file mode behavior, credential permissions, branch rules and safe size caps. If exact mode or strict incarnation is required but unavailable, retain refusal. Any eventual tests use synthetic disposable trees, fake GitHub and fake credentials only: assert no dispatch on changed repository/ref/head/credential, unsafe paths, links, unknown modes, duplicates, oversized inputs and expired/consumed approval; exercise A→B→A and ref deletion/recreation without pretending preflight detects them; concurrent writers, mutation rejection, 200 plus GraphQL errors, timeout/partial response, crash at each durable boundary, duplicate input and same clientMutationId; assert one dispatch maximum and operator-only unknown recovery. Explicit separately approved private-target testing would be a later decision and is not part of this research.
