## Status and boundary

This is a proposal, not an implemented adapter, an approved deployment policy, or evidence about the selected repository, host, hostname, web server or their configuration. The owner selected a disposable test repository (`main`) and a separate hostname for the website. Target identifiers belong in protected configuration, not this proposal. The existing separate Pilot test instance already occupies the previously discussed hostname; it is not a website virtual host and must remain unchanged. Selection does not authorize access or deployment in this investigation. No live service, repository or host was contacted or modified. Oracle here means the selected self-hosted target, not an assumed Oracle API or provider-managed deployment product.

The owner selected a minimal static HTML placeholder with no build step, to be exposed only through owner-authenticated Access. The proposed smallest first release is **already-built static files only** to one pre-existing host and a separately verified, pre-existing website virtual host. No website virtual host is established by this document; any routing or provisioning needed to create one requires separate authorization. There is no checkout, fetch, build, package install, arbitrary command, server configuration, DNS, TLS, provisioning, push, or credentials supplied by an agent. It does not support dynamic services, runtime code on the host, mutable data or database migrations. Browser-executed JavaScript is still code with network and user-data effects; static hosting is not a content security guarantee. The owner must accept the content and its public exposure. No install or deployment is authorized by this document.

## Existing seams and their limits

- `src/shared/ci-deployment-contract.ts` and `src/shared/cloudflare-target.ts` are strict identity/validation prototypes; neither proves provenance, config ownership or provider effects. They do not model a host release protocol.
- `src/server/agents/accepted-deploy.ts` is an injected Worker-version experiment, not an installed host adapter. Its Worker-specific version ID and `production` assumptions must not be repurposed as artifact provenance. `cloudflare-worker-deploy.ts` deliberately refuses writes. `tests/server/accepted-deploy.test.ts` uses a synthetic effect and intercepted reads.
- `ActionTargetStore` provides owner-written revisioned definitions and fingerprints, not a verified host identity or host-specific configuration. `AcceptedActionExecutor` binds acceptance, durable intent and a canonical resource key, and reports uncertain effects without retry; it is uninstalled and requires a named agent's self-acceptance under full-auto, not an owner-reviewed deploy flow. Resource serialization is Pilot-local, not a lock on other host writers. Read-only history does not resolve uncertainty. These are candidate seams, not an integration or proof of end-to-end safety.
- `docs/ACCEPTANCE.md` explicitly says completion evidence is self-reported and the runner provenance bridge is not installed. A digest or accepted claim alone cannot establish a build came from the selected `main` or that tests actually ran.

## Proposed fixed v1 release contract

All details in this section are a design to review, not properties verified on the host. The owner separately configures one immutable, revisioned, disabled-by-default target: project and selected repository stable identity; branch exactly `refs/heads/main`; host identity and pinned SSH host key; dedicated restricted deployment identity; one pre-created release root and one pre-configured web virtual host/hostname; and an exact externally reachable HTTPS origin and health path. No agent chooses or changes any of these, a path, remote, URL, command, port, credential, hook or server configuration. Owner identifiers and paths belong only in protected configuration, never a public document or model output. Host key rotation or any target change creates a new disabled revision requiring owner confirmation. A target digest binds the complete canonical configuration, including host key and web mapping; syntax/hash checks alone do not establish the mapping is true.

The host-side helper is a separately installed and audited fixed protocol endpoint, bound to that dedicated identity and release root. It accepts only bounded versioned structured requests for **stage**, **activate**, **inspect**, and a separately authorized **rollback**, never command strings or destination paths. Authenticate the helper and pin the host key; prohibit interactive shell, forwarding, PTY, arbitrary commands and unrestricted file transfer for that identity. Verify actual OS permissions, ownership, key restrictions and web-server mapping before any enablement; restrictions are requirements, not claims about the unknown host. Helper installation and host setup are out of scope. If the host cannot enforce this protocol and least privilege, refuse rather than substitute raw shell/SSH or a broad SFTP credential.

### Artifact and provenance

1. An independently trusted builder/observer must take an immutable full commit object ID from the selected repository's exact `main`, with a trusted observation binding repository identity, ref and commit at a stated instant. Decide and document whether deployment requires that commit still be the current head at admission; proposed default is yes, fail closed on stale or unverifiable head. The model cannot choose an arbitrary repo or assert this observation. Branch movement immediately after observation remains a race unless the source system offers a stronger verified mechanism; do not call it an atomic main-head guarantee.
2. The builder outputs a canonical manifest of relative paths, byte sizes and SHA-256 content digests, in bytewise path order, plus a format version and total bytes. Release ID is the SHA-256 of a domain-separated canonical manifest encoding. Restrict to regular files/directories; reject absolute paths, empty components, `.`/`..`, backslashes, duplicate or case-colliding paths, control characters, symlinks, hard links, devices, archives with unsafe entries, and configured count/per-file/total/path bounds. Require `index.html`. Specify the exact encoding, character set and bounds before implementation; no executable bits or ownership metadata are honored. Ingest through descriptor-relative no-follow operations resistant to directory replacement, not path normalization alone. Serving policy, MIME types and any client scripts need separate owner review.
3. A protected builder attestation binds repository identity, observed ref/commit, build recipe and toolchain/lockfile identity, output manifest/release ID, test receipt identity and builder identity. The trusted observer verifies actual bytes against the manifest immediately before staging; the host independently verifies the same digest after staging. The attestation must be authenticated by an authority protected from the model and the deploy caller, not merely a self-supplied JSON signature or hash. Reproducibility, if available, is additional evidence, not a substitute for trust. No existing Pilot runner currently provides this bridge; without it deployment is unavailable.
4. Pin the release ID, provenance/attestation digest, source commit, exact target revision/digest, expected active release, expected host generation and a unique action ID into a domain-separated action binding. The preview displays sanitized identity and evidence; acceptance applies to this complete binding, not just a branch, version label, or selected directory. Re-check authority and binding before the effect. No secret or raw deployment endpoint in receipts or logs.

### Target, stage, activate and health

A preflight read from the authenticated helper must establish exact target, helper protocol/version, host generation, active release and release root mapping. Stage under a fresh operation ID, stream only verified regular file bytes, enforce bounds, fsync files and directories, verify the final manifest, then seal an immutable release under the digest. No symlink traversal, overwrite of an existing different release, deletion of other releases, or serve-before-verification. If an existing digest is reused, re-verify it and its immutable ownership; a digest-shaped directory name is insufficient. The helper must protect release files against subsequent modifications by the uploader, web user and unrelated writers, or activation is refused. A helper running under the same UID as an untrusted Pilot shell cannot provide that protection.

Activation is a single durable helper operation: compare the observed active release and generation with the accepted expected values, atomically switch the pre-configured web root pointer to the sealed release on the same filesystem, persist the new generation and operation receipt, and only then acknowledge. Crash ordering, fsync and recovery must be specified and fault-tested; pointer rename and SQLite writes on separate systems are not one transaction. The helper must return an inspectable authoritative operation state, distinguishing not-started, committed, and unknown, and must reject duplicate operation IDs with different bindings. This is a **required implementation property**, not a claim that ordinary SSH, rename, or an existing Oracle host provides it. No external host writer may bypass the helper; otherwise compare-and-swap is not an enforceable concurrency boundary. Failure to prove exclusive authority stops activation.

After activation, compare helper read-back of active ID/generation and manifest to the intent. A separately authenticated local web-server check must verify that the configured virtual host actually serves the candidate, followed by an HTTPS request to the exact configured origin/path with certificate and hostname validation, redirects disabled, bounded response/deadline, and an expected digest of a fixed file from the manifest. The origin may be cached, proxied or point elsewhere: these observations demonstrate only what they actually observe, not global propagation, integrity of every file or content safety. Health failure is `activated-health-failed` or `health-unknown`, not proof activation failed. Never automatically roll back or redeploy on a failed/ambiguous check. Even a successful health response is not an authorization receipt or proof of provenance.

### Rollback

Rollback is a distinct owner-authorized action binding the same target revision, observed current release/generation and an explicitly selected previous sealed release and its verified manifest/provenance. It uses the same exclusive helper CAS, durable intent, inspection, health and uncertainty rules. Refuse if the previous release is unavailable, changed, untrusted, or the current pointer/generation differs. Switching files back cannot undo client-side effects, cached assets, traffic or data changes. Do not infer the prior release from a failed response or perform cleanup. No automatic rollback, retries or garbage collection in v1.

## Exact proposed policy and uncertainty

Default is disabled and deny all. Owner must explicitly enable this one target revision, grant the named agent access to this project and the distinct `deploy` scope, and separately choose `agent-may-accept` with `deploy=full-auto` if unattended deployment is desired. Every other action class remains `ask`; this instance-wide acceptance policy is not itself a per-target or per-agent boundary. Admission must independently enforce the exact target, the immutable artifact binding, project/session/agent identity, current target and policy revisions, source and builder evidence, expected active state, and resource fence. If the owner instead requires owner review, a distinct owner-reviewed, target-specific single-use approval implementation is needed; the existing executor does not implement it. The owner chooses the mode; this document does not switch policy.

Persist an intent and per-canonical-host-root resource barrier before sending any stage/activate/rollback request; serialize all aliases and all Pilot processes against it. Record phase-specific receipts with verified action binding and helper operation ID. Before any message can have been sent, a provable local refusal can be `not-started`; after handoff, timeouts, transport loss, cancellation, crash, malformed replies, failed receipt persistence and uncertain helper recovery remain `unknown`, even if an abort was requested. On restart retain the barrier and surface the uncertainty. Never automatically replay, create a fresh action to bypass it, release the barrier because a timer expired, or conclude no effect from a missing response. Stage can have partial effects even before activation. Reconciliation must be read-only and authenticated against the helper's durable operation journal, inspect pointer/generation and staged digest, and retain contradictory/missing observations as unknown. A separately authorized owner recovery procedure may clear a barrier only after independently establishing helper quiescence and recording the evidence; its protocol and permissions still need design and review. A restored/rolled-back control database or helper journal can erase barriers; backup rollback detection and cross-system authority remain unsolved, so refuse after suspected state rollback.

The helper and all Pilot code run on real hosts, not in a sandbox. Same-UID shell may access credentials, target configuration and the durable store, issue network requests and bypass named action scopes. No deploy policy limits arbitrary shell or malicious website code; protect the helper and credentials with a distinct OS authority and do not grant shell where that threat is unacceptable. Revalidation before sending is admission, not a revocable lease; an in-flight host effect may finish after scope revocation. Separate privileges, external administrators, host compromise, DNS/proxy compromise, and other writers are outside the Pilot-local fence.

## Owner choices and blocking facts

Already selected: a disposable repository, its `main` branch, and a website hostname separate from the existing Pilot test instance. Before implementing an enabled adapter, owner action or factual verification is still needed for:

1. Define the placeholder's exact source path and deployment artifact authority and size limits; the selected first version is static HTML with no build step and owner-only access. Any client-side scripts or external resources require separate review. If it requires SSR, mutable server data, build-on-host or runtime secrets, this design does not apply.
2. Choose the trusted builder/observer and authenticated provenance authority, including how `main` is observed and how tests are independently attested. The existing self-reported evidence and runner cannot supply this today.
3. Verify the chosen separate website hostname, intended disposable host and pre-existing web root, origin/health file and TLS path; authorize a dedicated restricted OS identity, fixed helper, host-key pin and exclusive writer arrangement. Verify these facts out-of-band; no host details or credential values are needed in this document.
4. Choose owner-reviewed single-use approval versus explicitly delegated full-auto, agent/project scope, retention limits and the owner recovery authority. Full-auto here does not authorize push, provisioning or general publication elsewhere.
5. Decide who installs/audits the helper and how its journal, keys, host privilege separation, backups and recovery are independently protected; specify fault-tested crash and restore semantics before enablement. If unavailable, retain the disabled state.

## Next validation gate

No code is added because a pure digest/parser alone would not resolve the missing trusted provenance and host authority, and no safe real transport is specified yet. A later uninstalled prototype should use disposable directories and an injected in-memory or local fake helper only: test canonicalization and malicious entries, target/config swaps, provenance mismatch, revocation races, concurrent aliasing, crash at every phase, lost reply after pointer switch, corrupt/stale journals, restoration, failed health, and separately authorized rollback. It must prove no network or live repository access in the fixture, preserve the uncertainty barrier across reopen, and demonstrate no automatic effect retry. Independent security review and explicit owner approval precede any real host setup. None of those tests would by itself establish real host isolation or deployed service health.
