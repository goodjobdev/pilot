# Runner dispatch/close and staged supervisor: investigation

**Disposition: no wiring.** This is an uninstalled design and characterization, not an implementation, service, deployment instruction, or proof of execution/termination. The baseline is the reconstructed integration worktree at `0cc6b82b36d8d40050ae0f2523e26f30ff808d72` plus its captured working-tree changes. Tests use disposable local roots and stub runtime calls only.

## Concrete incompatibilities

- `RunnerDispatchArbitration` commits an exact-request tombstone or a one-shot `dispatch-possible` decision in its own SQLite database. `RunnerSupervisor.submit()` never consults it; `requestCancellation(jobId)` only marks an already admitted supervisor row uncertain and throws for an absent job. A close before a delayed submit therefore cannot fence the supervisor. The new characterization test demonstrates this counterexample, not an accepted integration.
- Calling arbitration first and then supervisor is not an atomic operation. If dispatch wins, close must report **unknown**, including while the winner is paused before supervisor admission; the winner can proceed after close. A timeout, an absent supervisor row, or an aborted connection cannot turn that state into `closed-before-dispatch`. A committed one-shot permission is neither evidence of invocation nor proof it cannot occur later. Conversely, merely calling close on an application-side broker is not a service-side tombstone.
- Each component has independent storage and a different permanent global barrier. Supervisor dispatch invokes the synchronous runtime prefix *inside* its own transaction and commits its stage afterwards; an effect followed by crash/commit failure is uncertain. Supervisor policy/budget are in another store and policy revocation can race dispatch. A simple adapter cannot make these operations atomic or prove a runtime stopped. The transport has no durable exact-request close protocol; its in-memory `requiresReview` latch does not survive replacement/restart and `close()` means transport shutdown, not request arbitration.
- Arbitration reopen checks do not establish freshness or existence. Exclusive provisioning is not recovery: deleting a journal and provisioning anew forgets a tombstone, as the characterization test shows. A schema-valid rollback/replacement can do the same. The supervisor constructor can also create a missing empty journal. Unkeyed hashes detect some accidental corruption, not deletion, rollback or coordinated rewrite. File modes and SQLite FULL/WAL do not supply an independently protected freshness anchor.

## Required design before a bounded integration

1. Define one service-owned, authenticated, bounded exact-request **dispatch and close** interface. Both requests must carry the same canonical complete envelope, including job ID, policy revision and snapshot digest; reject changed content under an existing ID. Close must be accepted independently of a prior submit/admission and commit a durable tombstone, including when the dispatch request is still in transit. A read-only lookup, client abort, broker settlement or transport disconnect is not close. Existing uninstalled TLS transport lacks the full host peer-identity and protected-state guarantees; do not expose either operation until those prerequisites are established.
2. Put arbitration and supervisor admission in **one transactional service authority** (or give a formally specified equivalent linearizable protocol). On an absent ID, `close` atomically records `closed-before-dispatch`, while `dispatch` atomically records the immutable request and `dispatch-possible` plus its supervisor admission/deadline and permanent unresolved barrier. If close commits first, every delayed dispatch and duplicate must observe the tombstone and no create/start may be invoked. If dispatch commits first, every close and duplicate returns `dispatch-possible`/unknown, never non-execution; a delayed winning continuation may still invoke the port. No response before durable commit. Different IDs cannot bypass the unresolved global barrier; close tombstones may be recorded even while that barrier is held. This is a conservative, potentially permanently unavailable system.
3. Treat the winning dispatch continuation as a single internal, non-transferable execution authority; never return a reusable client token or allow a duplicate to continue it. If it dies after commit, recovery inspects only, never replays create/start or manufactures non-execution. Persist staged intent and immutable returned identity; failures between admission, create, identity, start and acknowledgement remain uncertain. A tombstone proves no service-authorized dispatch only if **all** paths to runtime obey the same authority and protected state is intact. If cancellation after dispatch is desired, it needs an independently specified exact-identity termination protocol and durable verified receipt; do not infer termination from close, timeout, a port's `exited` claim or cancellation.
4. Provision an independently protected existence **and freshness** anchor binding journal identity, generation and committed history, not just a second file subject to the same rollback. Specify privilege separation, atomic/ordering protocol across anchor and SQLite, crash recovery and fsync assumptions: any mismatch, missing/ambiguous anchor, stale database or interrupted update closes admission and requires audited operator investigation. Neither database nor anchor can silently initialize after loss; initial provisioning must be a separate privileged ceremony. The [external-anchor investigation](runner-journal-external-anchor-investigation.md) explores one unimplemented protocol and its assumptions. This is a design requirement, not an implemented algorithm: updates across two durability domains require a reviewed protocol that never treats either possible crash ordering as authorization to dispatch. Host root/kernel and actual storage durability remain trust assumptions.
5. Keep policy and budget conservatively enforced. Define whether revocation must fence already admitted but undispatched effects; if so, include its authoritative revision in the same serialization boundary or use a separately proven fencing protocol. Never refund an uncertain reservation. Specify authorization for close without allowing an untrusted client to close another request, and how tombstones are retained forever or garbage-collected without permitting old delayed messages. Define bounded storage/capacity exhaustion as fail-closed, not tombstone eviction.
6. Only after independently verified immutable runtime/cgroup identity, cgroup emptiness, no restart path, protected receipt and audited resolution may any terminal transition release capacity. Missing, malformed, conflicting, stale or unauthenticated evidence and failed termination retain the barrier. The staged stub `inspect` is not that evidence. No host capability or application feature should be enabled by this prototype.

## Acceptance tests for a future implementation

Use independent processes and disposable stores, deterministic gates around transaction boundaries and runtime stub invocation, and timeouts that reap every worker. Test both race winners, delayed dispatch delivered after durable close (also after reopening), duplicate and changed-content calls, concurrent distinct jobs, close after permission but before continuation, and a paused continuation resuming after close. Inject process death before/after each relevant commit and around create/start and lost replies; verify restart never invokes a second effect or reports non-execution for a possible dispatch. Test missing, rolled-back, replaced and contradictory journal/anchor states, both sides of interrupted anchor update, corruption and storage failure; every unprovable state must disable admission. Test policy revision races, budget preservation and exhaustion; test that fabricated inspection, unavailable runtime, cancellation and timeout never release the barrier. Crash tests are not power-loss durability proof: additionally review storage ordering and independently exercise the selected host, identities, peer authentication, runtime/cgroup limits, descendant termination, daemon restart and reboot. No live projects, credentials or network effects in tests.

## Characterization run and limits

`tests/server/runner-arbitration-supervisor-characterization.test.ts` records three negative observations: a tombstone does not stop the separate supervisor; committed permission remains possible after close/reopen without proving supervisor invocation; and reprovisioning a deleted journal forgets its tombstone. Existing arbitration tests cover one process race and clean reopen; existing supervisor tests manually reconstruct stage windows and use stub ports. These are narrow code-level observations, not proof of host isolation, physical durability, crash recovery, or safe interoperability. The two experiments remain uninstalled and no existing production route is changed.
