# Disposable runner supervisor authority: integration decision

**Disposition: no integration.** The existing single-authority fixture is a closed, three-field model with array effects; it is not the staged supervisor. Wrapping `RunnerSupervisor.submit` with that model or `RunnerDispatchArbitration` cannot make it the authority: callers can still invoke the supervisor directly. Its journal's `admit`, `dispatchCreate` and `dispatchStart` are separately callable as well. A tombstone in one database does not fence those paths in another. A test-only wrapper, shared filename, or returned permission would leave that bypass intact. No production endpoint, runtime or host configuration is changed here.

## Counterexample and scope

`tests/server/runner-supervisor-arbitration-process-characterization.test.ts` runs the actual uninstalled staged supervisor in a separate process with synthetic create/start ports and a disposable policy/control root. The worker waits until another process has committed an exact-request arbitration close, then invokes the supervisor without consulting that database. The synthetic create or start is reached despite the durable close. The worker is killed at that port; on reopen, the supervisor returns its existing row, does not replay either port, and rejects another job. In the start case, inspection observes `exited` using the persisted runtime identity and request digest, but cannot release the barrier. In the create case no runtime identity was persisted, so inspection does not call the runtime port and the barrier remains. Depending on scheduling, SIGKILL may arrive before or after the dispatched-stage commit; neither outcome demonstrates physical power-loss durability. The close record still says closed-before-dispatch, demonstrating why it must not be interpreted as a supervisor fence. Passing these tests means the **counterexample** was reproduced, not that integration is safe.

The existing `runner-single-authority-prototype.test.mjs` separately exercises close-first, dispatch-first, duplicates, delayed continuation and crashes for the closed fixture only. Those tests do not exercise the staged supervisor. The cross-process characterization does not prove behavior under every interleaving. It was run on the local development OS, not an independently verified Linux service host.

## Necessary bounded refactor before an integration experiment

1. Replace, not wrap, the supervisor journal's admission with one service-owned SQLite transaction for the complete canonical `RunnerServiceRequest`: exact-request tombstone or immutable dispatch-possible admission including deadline and permanent unresolved barrier. Close on an absent request must commit independently of supervisor admission; changed content under an ID must be rejected. A new close may be recorded while another dispatch occupies the barrier. Keep first-commit ordering across processes and never reply before commit.
2. Make the supervisor's synthetic create/start progression use that same authority and same committed admission. The first successful `submit` owns the sole in-process continuation; duplicates and reopened instances only inspect. Do not expose a reusable permission, a public continuation entry point, or the old independent journal path as another way to reach the runtime. Runtime ports and internal stage-mutators must not be reachable from other service dispatch paths; verify all call sites, not just a wrapper. An API/ownership refactor of the current exported classes is required before that claim is credible.
3. Commit each create/start intent before invoking the corresponding port and preserve immutable returned identity and acknowledgement validation. After admission, close returns dispatch-possible even if the winning continuation is delayed or dies; it cannot revoke that continuation. Any failure, lost reply, timeout, crash, inspection or synthetic completion leaves the global barrier permanent. Never resume or replay an effect after restart. Do not infer runtime termination.
4. In disposable Linux processes, use bounded gates and reaped workers to verify close-first across reopen and delayed delivery; dispatch-first close while paused and later continuation; duplicate/changed requests, distinct-job barrier and tombstones; SIGKILL before/after admission and around both ports, including lost replies. Assert no second port invocation and no non-execution claim after possible dispatch. Verify that every actual staged supervisor create/start route shares the authority, including direct/internal call attempts. These are tests of an experiment, not a substitute for host/storage review.

This proposal intentionally does **not** solve protected journal existence/freshness, authentication, independent policy/budget atomicity, runtime identity, real termination, exhaustion/retention or host isolation. Policy and budget currently live in a different store; a refactor must not imply revocation is atomic with dispatch or refund uncertain reservations. A deleted/replaced/rolled-back journal can forget a tombstone. Until a separately reviewed external freshness protocol and the other prerequisites in `runner-arbitration-supervisor-investigation.md` exist, this is not a deployable runner or evidence for one.

## Partial internal journal step (not integration)

The uninstalled supervisor journal now has an internal exact-request close operation in the same SQLite transaction domain as its existing admission. A close-first tombstone prevents that journal's later admission of the same request; an admission-first close reports dispatch-possible. Tombstones do not consume the unresolved-job barrier, and a different request under the same ID is rejected. The journal schema is now version 5 and refuses older schemas rather than migrating them; disposable experiment journals must be recreated, never treated as recovery of evidence.

This is **not** the proposed single-authority refactor. The journal and its admission, stage mutators and effect-dispatch methods remain publicly callable, the supervisor does not expose or own this close operation, and the separate `RunnerDispatchArbitration` remains unrelated. Existing cross-process counterexample tests still demonstrate that closing that separate arbitration cannot fence supervisor dispatch. The initial journal tests exercised separate handles and reopen; later same-journal process tests are described below and still do not cover the full requested interruption matrix. No deployed runner or production authority is implied; all limitations above remain.

### Same-journal process characterization

`runner-supervisor-same-journal-process.test.ts` now exercises the actual staged supervisor in a child process against the same journal database used by close in the parent. It checks a close committed before delayed submission, admission before close with a delayed create continuation, changed content, duplicate submissions, the distinct-job barrier, tombstones, and killed workers at synthetic create and start ports with no replay after reopening. These tests use disposable roots and synthetic ports. The process gates pause after admission, not between the admission commit and entry to create; they do not cover every crash window or physical power loss. The direct journal close used in these tests is not an owner-facing supervisor API and does not remove the exposed mutator bypass. The separate-database counterexample remains valid. The crash-stage and integrity test migrations described below do not establish production safety or a usable runner.

### Cancellation test migration

The cancellation-before/after-start-dispatch test now drives the supervisor through `submit` and `requestCancellation` rather than constructing stages or calling journal dispatch mutators. A clock callback observes `start-intent` and requests cancellation before dispatch; a gated synthetic start port tests cancellation after invocation and its delayed completion. The test checks the persisted stage, retained identity, zero or one invocation, uncertainty and duplicate no-replay. This is a test migration, not an ownership change: `dispatchStart` remains public because the supervisor and other integrity and crash-stage tests still call the journal directly. The pre-dispatch case exercises an in-process injected clock callback, not an independently ordered process race. Subsequent test migrations below replace direct-mutator setup for selected crash-window and integrity cases while retaining their stage-level assertions.

### Identity-integrity test migration

The runtime-ID and malformed-identity integrity tests now reach `identity-recorded` through the staged supervisor's actual synthetic create port. A disposable SQLite trigger injects failures on subsequent start-intent and uncertain writes, leaving the original identity-recorded row available for the same corruption assertions; the trigger is removed after a bounded submit drain. The uncertain-identity case then uses supervisor cancellation. These tests retain direct SQL only for fault injection and evidence corruption; they do not call journal dispatch mutators. This does not make the mutators private: the staged supervisor and other journal-integrity tests still call them, and callers can still directly invoke journal admission, transition, `dispatchCreate` and `dispatchStart`. The runtime is still supplied to the exported supervisor. This is test migration, not single-authority integration, authentication, freshness, or containment.

### Crash-stage and transition-evidence test migration

The seven-stage reopen/no-replay test now uses actual supervisor submissions and synthetic runtime ports. Stage-specific SQLite triggers inject a write failure while also blocking the uncertainty update, preserving each staged row for reopen; they are removed after bounded drainage. Because the supervisor invokes ports before committing dispatched-stage updates, the create-intent and start-intent cases deliberately assert that a port can already have been invoked even when the stage update fails. This is a simulated persistence failure, not process death or physical power loss. The stage-integrity digest test now observes every inserted/updated stage using connection-local temporary audit triggers while driving the supervisor, preserving all eight distinct-digest assertions without journal dispatch mutators.

The private-authority refactor remains undone. In addition to the separate arbitration database, `RunnerSupervisor` accepts an externally owned `RunnerSupervisorJournal` and runtime, and the journal publicly exports its SQLite handle, admission, transition and dispatch methods. TypeScript `private` fields alone would not remove those paths. Closing only through a wrapper or moving tests alone would not fence a caller holding the journal or runtime. No new supervisor close API, authority claim, schema migration, authentication, freshness or containment guarantee is added here.

## Separate closure-private synthetic experiment (not staged-supervisor integration)

`tests/server/fixtures/runner-closure-authority.ts` is a separate test-only synthetic authority. Its SQLite handle, close/admit transaction, stage mutators and no-op synthetic create/start progression are lexically private to each opened authority. The only public instance operations are submit, exact-request close and disposal; neither admission permission nor a continuation is returned. Its trusted hooks only observe or pause named synthetic stages and are not runtime ports. A first committed admission owns the sole continuation, duplicates never resume, close-first tombstones and admission-first dispatch-possible share one SQLite journal, and an unresolved admitted job permanently blocks distinct admissions. The complete parsed request and deadline are integrity-bound; expiration or hook failure leaves dispatch-possible and does not release the barrier. The fixture's schema is independent version 1 and rejects incompatible versions rather than migrating them.

`runner-closure-authority.test.ts` checks API shape and direct access attempts, exact and changed requests, the barrier, hook failure and deadline, corrupted evidence and incompatible schema, and bounded cross-process close-first, admission-first continuation, and killed-worker reopen/no-replay at each synthetic stage. These tests use trusted hooks and no-op effects: they do **not** test the actual staged supervisor or a real runtime, establish authentication or protect against journal deletion/replacement/rollback, or prove policy/budget atomicity, containment or termination. The existing staged supervisor remains unchanged with its exported journal, separately supplied runtime and public mutator bypass; its separate-database counterexample still applies. This experiment is not installed or usable for production execution.

### Synthetic effect-boundary observations

The closure-private synthetic create and start functions now invoke a trusted synchronous observation hook at their actual invocation boundaries. The observer independently opens the same database read-only and records the committed request, decision, deadline and stage. Tests require `create-intent` at create and `start-intent` at start, and check zero, one or two observations across close-first, a released admission-first continuation, interruption at each stage, and reopen/duplicate submission. The child writes at most eight small records to a disposable file; parent reads are size-capped, and workers are bounded and reaped. Mutation checks removing either synthetic port invocation make the expected two-effect assertion fail.

These observations are trusted test instrumentation: the callbacks and disposable file are not protected receipts, are not fsynced power-loss evidence, can block or throw, and do not prove an external runtime effect occurred. Synthetic functions remain no-op host-wise, are not exported, and no callable continuation is exposed. The actual staged supervisor and its public bypass remain unchanged; none of the authentication, freshness, storage, policy, containment or termination limitations is resolved.
